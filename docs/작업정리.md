## 1. 구성 한눈에 보기

```
브라우저
 └─ 메인 화면  site/index.html  (정적 HTML 1개)
      └─ AI 상담 위젯(iframe) ──▶ 챗봇  frontend/ (React)  ── /chat/
                                   ├─ 메인(주간/야간) · ⚙ 설정 · 질문 입력 바
                                   └─ 연결 페이지(iframe)  frontend/public/pages/*.html  ── /pages/
                                        ▲  postMessage('chatpoc:query', {text, topic})
                      (사내 서버, Docker 컨테이너) 백엔드  backend/ FastAPI + 챗봇 화면을 함께 제공
                          ├─ GET  /v1/config         ← 없으면 목업(mockConfig)으로 동작
                          └─ POST /v1/chat/messages  ──▶ 사내 LLM (실패하면 대체 모델 → 키워드 규칙)
```

| 경로 | 역할 | 소스 |
|---|---|---|
| `/` | 병원 홈페이지형 메인 화면, AI 상담 위젯 | `site/index.html` |
| `/chat/` | 챗봇 앱 | `frontend/src/` |
| `/pages/*.html` | 챗봇 안에서 여는 연결 페이지(오시는 길, 증상별 진료 안내) | `frontend/public/pages/` |
| (사내 서버) `/v1/config`, `/v1/chat/messages` | 메뉴·운영시간·면책 문구 설정, 질문 분류 | `backend/app/` |
| (사내 서버) 컨테이너 배포 | 사내 서버에 챗봇 컨테이너만 추가하는 compose 구성 | `docker/chatpoc/` |

**질문 하나가 처리되는 흐름**

1. 사용자가 입력 바에 글자를 쓰거나 추천 질문을 고른다 (`ChatInputBar`).
2. `App.ask()`가 판별한다.
   - 추천 질문: 엑셀에서 정한 기능으로 이동 (`routeSuggestion`, 응급 검사만 먼저)
   - 직접 입력: **응급 규칙 먼저** → 서버(LLM)가 있으면 서버로 분류 → 서버가 없거나 실패하면 키워드 규칙(`routeQuestion`)
3. 결과에 따라 **응급 안내(119)** / **연결 페이지로 이동** / **"준비중" 안내** / **모르겠음 + 추천 메뉴**.
4. 이동하면 `PageViewer`가 iframe으로 페이지를 열고, 입력 문구와 주제(topic)를 `postMessage`로 전달한다.
5. 한 문장에 요청이 여럿이면 첫 번째로 이동하고 나머지는 입력 바 위의 칩으로 이어서 연다.

## 3. 기능별 상세

각 기능은 **무엇 / 어떻게 / 사용한 스킬 / 설계 이유 / 검증** 순서로 쓴다.

### 0. 챗봇 기본 화면과 설정 API

**무엇** — 챗봇을 열면 병원 이름, 상담원 연결 버튼, 인사말, 큰 배너(진료 예약), 메뉴 타일 4개, 자주 찾는 질문 칩 4개가 보인다. 상담원 운영시간(평일 08:30–17:30)이 아니면 **야간 화면**으로 바뀐다 — 콜백 요청 버튼과 119 응급 안내 카드.

**어떻게**
- 화면은 서버가 주는 `ChatConfig`(병원명, 운영 여부, 히어로, 타일, FAQ, 면책 문구)로 그려진다. `App.tsx`가 `GET /v1/config`를 부르고 실패하면 `mockConfig.ts`로 대체한다.
- 운영 여부는 **서버가 KST 기준**으로 판단한다(`zoneinfo`, 주말·휴일 집합 제외). 사용자 기기 시간은 쓰지 않는다.
- 데모용으로 `?night=1`을 붙이면 야간 화면을 강제로 본다.
- 메뉴 항목에는 `intent`(기능 키, 예: `info.directions`)가 있고, 이 키가 연결 주소·질문 판별·추천 질문을 잇는 공통 열쇠다.
- 면책 문구("AI 안내는 참고용이며 진단이 아닙니다")는 관리자가 비워도 기본 문구로 강제 노출한다(프론트·백엔드 양쪽).

**사용한 스킬**
- FastAPI + Pydantic v2: `CamelModel`(`alias_generator=to_camel`)로 파이썬 snake_case를 TS의 camelCase로 변환, `response_model_by_alias`
- 시간대 처리: `zoneinfo.ZoneInfo("Asia/Seoul")`
- CORS 환경변수(`CORS_ORIGINS`), Dockerfile(`python:3.12-slim`, uvicorn)
- React 18 훅(`useState`/`useEffect`), `fetch` + 실패 시 대체 데이터
- CSS Modules, 인라인 SVG 아이콘(`icons.tsx`)

**설계 이유**
- 백엔드가 없어도 프론트만 배포해 데모할 수 있어야 해서 목업 대체를 뒀다. 이 덕분에 GitHub Pages(정적 호스팅)만으로 지금 사이트가 동작한다.
- 운영시간 판단을 서버에 둔 것은 사용자 기기 시계를 믿을 수 없기 때문이다.
- `intent` 키를 한 곳에서 정하고 여러 기능이 같은 키를 쓰게 해서 기능 간 연결이 키 하나로 끝난다.

### 1. 병원 메인 화면 클론

**무엇** — 실제 병원 홈페이지 메인의 레이아웃을 참고한 HTML 한 파일. 로고·기관명·문구·사진은 모두 가상("3팀 / 우리팀 챗봇 POC").

**어떻게**
- 구성: 헤더 → 메인 비주얼 슬라이드 3장 + 빠른예약 바 → 소식 카드 → 미디어센터 → 새로운 소식(탭 필터) → SNS → 푸터
- PC는 섹션별 한 화면(`scroll-snap-type: y mandatory`), 900px 이하(모바일)는 스냅 해제하고 한 줄 배치
- 색·높이는 `:root`의 CSS 변수(`--navy`, `--header-h` 등)로 관리
- 슬라이더·탭은 바닐라 JS (프레임워크 없음)

**사용한 스킬** — HTML5 시맨틱 마크업, CSS 변수(디자인 토큰), Grid/Flexbox, `scroll-snap`, 미디어 쿼리(1200px·900px), 바닐라 JS(슬라이더 자동 전환·점 내비게이션)

**설계 이유**
- 챗봇을 "실제 홈페이지 안에서" 보여 주려는 목적이라 정적 HTML 한 파일로 충분했고, 빌드 없이 열어 볼 수 있다.
- 실제 기관의 로그인 화면 복제는 피싱 오해 소지가 있어 제외했다. 실제 기관 정보·로고도 넣지 않는다.

### 2. 메인 화면 AI 상담 위젯

**무엇** — 오른쪽 아래 **AI 상담** 버튼을 누르면 챗봇이 메인 화면 위 창(PC 420px, 모바일은 전체 화면)으로 열린다. ESC로 닫고, 다른 버튼에 `data-chat` 속성을 붙이면 같은 창이 열린다.

**어떻게**
- 챗봇은 iframe이고, **처음 열 때만 `src`를 채워** 메인 로딩을 늦추지 않는다.
- 불러올 주소는 상황에 따라 다르다.

| 메인 화면을 연 곳 | 챗봇 주소 |
|---|---|
| 배포 사이트 | 같은 사이트의 `chat/` (`new URL('chat/', location.href)`) |
| 내 PC + 개발 서버(`localhost:5173`) 켜짐 | 개발 서버 (800ms 안에 응답하면) |
| 내 PC + 개발 서버 없음 | **위젯 폴백(로컬용 대체 주소)** = 배포된 `/chat/` (`CHATBOT_URL`) |

- 위젯 폴백은 내 PC에서 열었을 때만 쓰이고, 창의 "새 탭에서 열기" 링크는 항상 이 주소를 가리킨다.

**사용한 스킬** — 바닐라 JS(즉시 실행 함수), iframe 지연 로딩, `fetch(..., { mode: 'no-cors', signal: AbortSignal.timeout(800) })`로 개발 서버 존재 확인, `location.hostname` 판별, `role="dialog"` + `aria-label`, 키보드(ESC)

**설계 이유**
- 메인 화면과 챗봇을 iframe으로 분리해 **스타일·스크립트 충돌이 없고 따로 개발·배포**할 수 있다.
- `/chat/`를 상대 경로(`new URL('chat/', location.href)`)로 계산해서 저장소 이름 하위 경로(`/hospital-chat-poc/`)에서도 수정 없이 동작한다.

### 3. 기능별 연결 주소 설정

**무엇** — 챗봇 헤더의 ⚙ 버튼 → 메뉴마다 눌렀을 때 열릴 주소를 등록한다. 항목은 메뉴 설정(`config`)에서 **자동 생성**된다.

**어떻게**
- 묶음: 메인 메뉴 5 / 자주 찾는 질문 4 / 질문으로 여는 화면 1 / 상담 2
- 허용 값: `https://` 주소 또는 같은 사이트 경로(`/pages/...`). `javascript:` 같은 주소와 `//`로 시작하는 주소는 거부(`isValidUrl`)
- 저장: 브라우저 `localStorage`(키 `chatpoc.links.v1`). 처음 여는 브라우저(저장값 없음)에만 기본값(`DEFAULT_LINKS`: 오시는 길, 증상별 진료 안내, 주차 안내) 적용. 한 번 저장하면 저장값이 우선하며 기본값을 지운 것도 유지된다
- 저장이 차단된 브라우저(사생활 보호 모드 등)에서는 `role="alert"`로 실패를 알린다

**사용한 스킬** — React 폼(제어 컴포넌트, `useMemo`로 그룹 생성), URL/정규식 검증, `localStorage` 예외 처리(`try/catch` + 안내), `aria-invalid`·`role="status"`·`role="alert"`·`label`

**설계 이유**
- POC라 서버 저장 대신 브라우저 저장을 썼지만, `loadLinks`/`saveLinks` 두 함수만 바꾸면 백엔드 저장으로 교체할 수 있게 경계를 좁혔다.
- 새 메뉴가 생겨도 설정 화면을 고치지 않도록 항목을 설정 데이터에서 만든다.

### 4. 미연결 메뉴 회색 처리

**무엇** — 연결 주소가 없는 메뉴(타일·진료 예약 배너·질문 칩·상담원 연결)는 회색으로 보이고, 누르면 "'메뉴명' 서비스는 준비중입니다"가 잠깐 나타난다.

**어떻게** — `App.isLinked(key)`가 `MainScreen`에 내려가 `muted` 클래스를 붙인다. 안내는 화면 하단 토스트(`role="status"`, 2초 후 사라짐).

**사용한 스킬** — React props로 상태 전달, 조건부 클래스, `role="status"`

**설계 이유** — 아직 연결 전인 기능을 숨기지 않고 보여 주면서 "준비중"임을 분명히 알려야 데모할 때 전체 모습이 드러난다.

### 5. 챗봇 안 페이지 이동, 오시는 길

**무엇** — 연결 페이지는 새 탭이 아니라 챗봇 안(`PageViewer`)에서 열리고 ← 버튼으로 돌아온다. 외부 사이트를 위해 "새 창" 버튼도 있다. 연결 페이지는 두 개를 만들었다.

- **오시는 길** (`directions.html`): 약도, 주소 복사, 전화 걸기(`tel:`), 지하철·버스·자가용 탭, 주차 안내
- **증상별 진료 안내** (`symptom.html`): 추천 진료과, 진료 전 확인 사항, 응급 신호(119)

**어떻게**
- 페이지가 챗봇 안에서 열린 것을 알아채면(`window.self !== window.top` → `embedded` 클래스) 본문 제목을 숨겨 중복을 막는다.
- 주소 뒤에 `#car`처럼 탭을 지정해 열 수 있다 (주차 안내 기본 연결이 자가용 탭).
- 증상 안내는 `GUIDE` 객체(주제별 데이터)를 DOM에 그리며 `textContent`만 사용한다(HTML 주입 없음).
- 외부 사이트가 iframe 표시를 막을 수 있어 "새 창" 버튼을 항상 제공한다.

**사용한 스킬** — iframe 임베드, Clipboard API(`navigator.clipboard.writeText` + 실패 안내), ARIA 탭(`role="tablist"`/`tab`/`aria-selected`), `location.hash` 처리, 모바일 우선 CSS, `textContent`로 안전한 렌더링

**설계 이유** — 사용자가 챗봇을 벗어나지 않고 안내를 보게 하려고 iframe을 썼다. 연결 페이지가 정적 HTML이라 나중에 실제 병원 페이지 주소로 바꿔 끼우기만 하면 된다.

### 6. 병원 이름 변경, 헤더 반응형

**무엇** — "OO병원" → "우리팀 챗봇 POC"(프론트 목업, 백엔드 `/v1/config`, 탭 제목 모두). 좁은 화면에서 이름·버튼이 줄바꿈되던 문제를 고쳤고, 400px 이하에서는 "AI 상담" 배지를 숨긴다.

**사용한 스킬** — 반응형 CSS(미디어 쿼리, `flex-wrap`/`min-width` 조정), 이름처럼 흩어진 값을 한 번에 찾아 바꾸는 검색

**설계 이유** — 병원 이름은 설정 데이터 한 곳(`config.hospitalName`)에서 나오게 해 두어 교체 비용이 낮았다.

### 7. 공통 질문 입력 바, 질문으로 화면 이동

**무엇** — 질문 입력창을 모든 화면 아래에 고정하고(설정 화면은 제외), 질문을 판별해 해당 화면으로 이동한다. 화면이 바뀌어도 입력 중인 글자는 유지된다.

| 입력 예 | 판별 | 결과 |
|---|---|---|
| 배 아파, 속이 쓰려요 | 소화기 증상 | 증상별 진료 안내 이동, 추천 진료과 소화기내과 |
| 머리가 아파요 / 기침이 나요 | 두통 / 호흡기 | 같은 화면, 신경과 / 호흡기내과 |
| 가슴이 아파요, 숨이 차요 | 응급(최우선) | 이동하지 않고 응급 안내 + 119 전화 |
| 병원 위치 알려줘 | 오시는 길 | 오시는 길 이동 |
| 주차 되나요 | 주차 안내(미연결) | "준비중" |
| 안녕하세요 | 판별 실패 | "이해하지 못했어요" + 연결된 메뉴 칩 |

**어떻게**
- 판별기 `routeQuestion`은 **우선순위가 있는 규칙 배열**이다. 위에서부터 먼저 맞는 규칙을 쓰므로 구체적인 규칙을 위에 둔다(예: "예약 조회"가 "예약"보다 위, "주차"가 "교통수단(차)"보다 위).
- **응급 패턴은 모든 규칙보다 먼저** 검사한다. 응급 문구가 다른 증상과 함께 있어도 응급이 이긴다("배가 아프고 숨이 차요" → 응급).
- 결과 형식은 판별 유니온 `RouteResult`(`emergency` / `intent` / `unknown`)다. AI 판별로 바꿀 때 이 형식만 지키면 호출하는 쪽은 바뀌지 않는다.
- 이동하면 말풍선은 닫고 화면 위쪽에 "입력하신 내용"만 표시한다. 이동하지 않을 때만 말풍선으로 안내한다.
- 입력 문구는 `postMessage`로 **같은 사이트 페이지에만** 전달한다(주소·로그에 건강 정보가 남지 않게).

**사용한 스킬** — 정규식 기반 한국어 키워드 판별(띄어쓰기·어미 변형 흡수), TypeScript 판별 유니온, 규칙 우선순위 설계, 안전 우선 설계(응급 먼저), `postMessage` + `origin` 검사, 테스트 주도 규칙 보강

**설계 이유**
- 규칙 기반으로 시작한 이유: 의료 도메인에서 응급 판별은 **예측 가능하고 항상 먼저** 동작해야 하므로, AI에 맡기지 않고 규칙으로 고정했다.
- 오탐 방지: "배송 문의", "배우고 싶어요"처럼 `배`가 들어가도 증상이 아닌 문장을 테스트로 고정했다.
- 증상별 진료 안내는 진단이 아니다. 면책 문구는 항상 노출한다.

**검증** — `intentRouter.test.ts`(27개): 증상 표현 변형, 응급 우선, 규칙 우선순위, 오탐 방지, 빈 입력

### 8. 챗봇 창 끌어서 이동

**무엇** — 메인 화면의 AI 상담 창 위쪽 바를 잡고 끌어서 옮긴다. 위치는 브라우저에 기억하고, 바를 더블클릭하면 원래 위치로 돌아간다. 화면 밖으로는 나가지 않고, 모바일(900px 이하)에서는 이동하지 않는다.

**어떻게** — `pointerdown`에서 `setPointerCapture`로 잡고, `pointermove`마다 `place(x, y)`가 화면 안으로 보정(`GAP` 8px)한다. 위치는 `localStorage`(`chatpoc.panelPos`)에 저장하고, 창 크기가 바뀌면 다시 맞춘다.

**사용한 스킬** — Pointer Events(마우스·터치 공통), `setPointerCapture`, `getBoundingClientRect`, `matchMedia('(max-width: 900px)')`, `localStorage` 예외 처리, `resize` 이벤트

**설계 이유** — 메인 화면의 내용을 가리지 않도록 사용자가 창을 옮길 수 있어야 했다. 모바일은 전체 화면이라 이동 기능을 아예 끈다.

### 9. 화면별 추천 질문 목록

**무엇** — 입력창을 누르면 **지금 화면에 맞는 추천 질문**이 펼쳐지고, 고르면 바로 전송된다.

**어떻게**
- 목록의 키는 화면(메인은 `home`, 연결 페이지는 그 기능의 `intent`)이다. 목록이 없는 화면은 메인 목록을 쓴다.
- 입력 중 걸러 보기: 띄어쓰기를 무시하고 글자가 **순서대로** 들어 있으면 일치한다("배아파" → "배가 아파요"). ↑↓·Enter·ESC를 지원한다.
- 같은 페이지에 새 질문이 오면 다시 불러오지 않고 메시지만 전달한다 → 오시는 길에서 "버스 노선"을 고르면 버스 탭으로 바뀐다.
- 키워드 보강: "병원 어떻게 가요?", "가는 방법", "길 알려줘", "응급실 위치" → 오시는 길. 지하철·버스·자가용 표현은 해당 탭 주제로 판별한다.

**사용한 스킬** — 콤보박스 패턴(`role="combobox"`/`listbox`/`option`, `aria-activedescendant`), 키보드 내비게이션, 순서 보존 부분 일치 알고리즘(`matchesQuery`), 입력 포커스 유지(`onMouseDown`에서 `preventDefault`), `postMessage` 프로토콜 확장(`topic`)

**설계 이유**
- 자유 입력은 어려운 사용자도 추천 질문만 눌러 쓸 수 있게 하려는 것이다.
- 화면에 맞는 질문만 보여 주면 질문이 해당 화면의 기능과 어긋나는 일이 줄어든다.

### 10. 추천 질문 엑셀 편집·연동

**무엇** — 추천 질문을 코드를 건드리지 않고 **엑셀에서 편집**하고 `npm run sync:suggestions`로 챗봇에 반영한다.

**엑셀 형식**
- `frontend/data/suggestions.xlsx`
- **'추천질문' 시트**: 질문 · 화면 · 연결 기능 · 순서 · 사용 (화면·연결 기능·사용은 드롭다운)
- **'목록' 시트**: 화면/연결 기능의 선택지와 내부 키(엑셀에 보이는 이름 ↔ 코드의 기능 키)

**어떻게**
```
suggestions.xlsx ──read-excel-file──▶ buildSuggestions(질문 행, 목록 행) ──▶ suggestions.json ──▶ 챗봇
                     (sync-suggestions.mjs)   (suggestionsFromRows.mjs, 순수 함수)   {"screens": {"home": [{text, intent, label}], ...}}
```
- **검증 후 쓰기**: 목록에 없는 값, 순서·사용 값 오류, 같은 화면의 중복 질문(띄어쓰기만 다른 것 포함)은 `'추천질문' 시트 N행: ...`처럼 위치와 함께 알리고 **파일을 바꾸지 않는다**.
- **연결 기능 우선**: 추천 질문을 누르면 키워드 판별기보다 엑셀에서 정한 기능으로 이동한다(`routeSuggestion`). 응급 신호 검사는 그대로 먼저 실행한다. 추천 질문과 똑같은 문구를 직접 입력해도 같은 기능으로 이동한다.
- **연결 여부와 무관하게 표시**: 연결 주소(⚙ 설정)가 없는 기능의 질문도 모두 보이고, 누르면 "준비중입니다"가 나온다. (기능 9의 "자동 숨김"에서 바꿨다 — 엑셀에서 '사용'으로 둔 질문이 사라져 혼란스러운 일을 막기 위함)
- "상담원 연결"을 추천 질문 기능으로 추가했다(상담 버튼과 같은 키 `action.agent`).

**편집 절차** — 엑셀 수정·저장 → `npm run sync:suggestions` → `npm test` → xlsx와 json을 **함께** 커밋 → PR → 머지(배포 워크플로가 동기화·빌드를 다시 실행).

**사용한 스킬** — 엑셀 템플릿 설계(데이터 유효성 검사 드롭다운, 안내 줄 `※`), Node 스크립트로 엑셀 읽기(`read-excel-file`), **순수 함수 + I/O 분리**, 사람이 읽을 수 있는 오류 메시지 설계(시트·행 번호), 생성 파일을 커밋해 원본과 결과를 같이 관리, Vitest 단위 테스트

**설계 이유**
- 비개발자가 가장 익숙한 도구가 엑셀이라 편집 UI를 따로 만들지 않았다. Notion·Obsidian 등과 비교해 가입·권한 없이 파일 하나로 끝나는 점을 택했다.
- 변환 로직을 순수 함수로 분리해서 엑셀 파일 없이도 테스트할 수 있다.
- 잘못된 엑셀이 챗봇을 망가뜨리지 않도록 "검증 실패 시 기존 JSON 유지"를 기본값으로 했다.

**검증** — `suggestionsFromRows.test.mjs`(10개): 정상 변환·정렬·중지 항목 제외·오류 위치. `suggestions.test.ts`(17개): 연결 기능 키가 챗봇이 아는 기능인지, 응급 문구가 아닌지, 판별기가 모르는 질문("상담원연결")도 정해 둔 기능으로 이동하는지.

### 11. GitHub Pages 자동 배포

**무엇** — `main`에 머지하면 GitHub Actions가 테스트 → 추천 질문 동기화 → 빌드 → Pages 배포를 자동 실행한다. 손으로 빌드·업로드하지 않는다.

**어떻게**
```
push(main) / 수동 실행
  └ build : checkout → setup-node(20, npm 캐시) → npm ci → npm test
            → sync:suggestions → SITE_BASE=/hospital-chat-poc/ build:site --out ../production-site
            → upload-pages-artifact(production-site)
  └ deploy: deploy-pages (environment: github-pages)
```
- 사이트가 **하위 경로**(`/hospital-chat-poc/`)에 올라가므로 빌드 때 환경변수 `SITE_BASE`로 알려 준다. `build-site.mjs`가 챗봇을 `${SITE_BASE}chat/` 기준으로 빌드하고, `DEFAULT_LINKS`는 빌드된 `BASE_URL`에서 사이트 루트를 계산한다.
- `SITE_BASE`를 비우면 도메인 루트(`/chat/`)로 빌드된다(로컬 확인용).
- 권한은 `contents: read`, `pages: write`, `id-token: write`만, 동시 실행은 `concurrency`로 막는다.
- 테스트가 실패하면 배포되지 않아 운영 사이트는 이전 상태로 유지된다.

**사용한 스킬** — GitHub Actions(트리거, 권한, 환경, 아티팩트 업로드·배포 액션), `npm ci`(잠금 파일 그대로 설치)·`setup-node` 캐시, 환경변수로 빌드 설정 주입, Vite API 직접 호출(base 지정), `import.meta.env.BASE_URL`, 하위 경로 호스팅 대응, Git 충돌 해결(PR #12)

**설계 이유**
- 이전에는 Netlify에 폴더를 끌어다 놓는 수동 배포라 머지해도 운영 주소가 바뀌지 않아 실수가 잦았다. Pages 자동 배포로 "머지 = 배포"가 됐다.
- `vite.config.ts`에 `base`/`outDir`을 박지 않았다. 박으면 `npm run dev`의 프록시·경로가 깨지고, 스크립트가 어차피 Vite API로 직접 값을 넘기기 때문이다.
- 조직 비공개 저장소는 무료 플랜에서 Pages를 쓸 수 없어 **저장소를 공개로 전환**했다. 데이터가 가상이고 비밀 값이 없다는 것을 점검한 뒤 결정했다.

**위젯 폴백 정리** — 배포 사이트에서는 폴백이 쓰이지 않는다. 내 PC에서 개발 서버 없이 메인 화면을 열 때만 `CHATBOT_URL`(Pages 주소)로 대체된다.

### 12. 직접 입력 질문의 LLM 분류, 복합 질문 이어보기

**무엇** — 입력창에 직접 쓴 질문을 사내 LLM이 어느 기능인지 분류한다. 키워드 규칙이 못 따라가던 구어체("차는 어디에 세우면 되나요", "무릎이 시큰거려요")와 한 문장에 요청이 여럿인 질문("주차 되나요? 그리고 지하철로 가는 방법도")을 처리한다.

**어떻게**
```
입력 ─▶ 응급 규칙 ─ 응급이면 즉시 119 안내
         │ 아니면
         ▼
   서버 있음? ─ 아니오 ─▶ 키워드 규칙 (이전과 같음)
         │ 예
         ▼
   POST /v1/chat/messages ─ 실패·시간 초과(5초) ─▶ 키워드 규칙
         │ 성공
         ▼
   기능 최대 3개 (말한 순서) ─▶ 첫 번째로 이동 + 나머지는 칩
```
- **서버(`backend/app/features/chat/`)**: 질문을 사내 LLM(OpenAI 호환 API)에 보내 `{"intents":[{"intent","topic"}]}` 형식으로만 답하게 한다. 서버 설정에서 출력 형식을 JSON 스키마로 강제한다(`response_format: json_schema`, 기능·주제는 정해진 값만 허용).
- **검증·정리(`service.normalize`)**: 모르는 값 제거, 같은 기능 중복 제거, **응급이 있으면 응급만**, `unknown`은 다른 기능이 있으면 버리고, 최대 3개로 자른다. 주제(topic)는 증상 안내·오시는 길에서만 쓴다.
- **모델 대체**: 1순위 모델이 실패하면(오류·형식 불일치) 2순위 모델로 넘어가고, 둘 다 실패하면 503 → 프론트가 키워드 규칙으로 대체한다.
- **프론트(`llmRouter.ts`, `App.tsx`)**: `/v1/config`의 `llmRouting`이 true일 때만 서버를 부른다. 응답을 기다리는 동안 "질문을 확인하고 있어요…"를 보이고, 그 사이 다른 질문을 보내면 이전 결과는 버린다.
- **이어보기**: 연결 페이지는 챗봇 안 화면 하나라 한 번에 하나만 열 수 있다. 그래서 첫 기능으로 이동하고 나머지는 "이어서 궁금하신 내용도 볼 수 있어요" 칩으로 보여 준다. 칩을 누르면 다음 화면으로 이동하고 남은 칩이 갱신된다.
- **실행**: 사내 AI 서버에 닿는 PC 1대에서 `uvicorn`으로 실행하고, `SITE_DIR`을 지정하면 같은 서버가 챗봇 화면까지 제공한다(같은 주소라 CORS 불필요). GitHub Pages에는 서버가 없어 규칙 모드로 동작한다.

**사용한 스킬** — FastAPI(의존성 주입, `dependency_overrides` 테스트), httpx 비동기 클라이언트, Pydantic 입력 검증(길이 제한), LLM 구조화 출력(JSON Schema), 프롬프트 설계(기능 목록·주제·규칙·출력 형식), 응답 검증·정규화, 모델 대체(failover), React 비동기 상태(요청 번호로 오래된 응답 버리기), `fetch` + `AbortSignal.timeout`, pytest(`MockTransport`로 LLM 대체), Vitest(`fetch` 스텁)

**설계 이유**
- **"규칙 먼저, LLM은 보완"이 아니라 "응급 규칙만 먼저, 나머지는 LLM"**: 규칙이 답을 낸 58건 중 6건이 틀렸고("버스 기사님이 친절하셨어요" → 오시는 길 등), 보완 방식은 그 오류를 그대로 물려받아 94.5%였다. LLM 단독은 100%(평가 기준).
- 사내 LLM은 인터넷 브라우저에서 직접 부를 수 없고(사내 주소, https→http 차단) 프롬프트가 화면에 노출되므로 **중간 서버**를 둔다.
- 답이 정해진 JSON 형식과 기능 목록으로 제한되어 이 서버로 일반 대화를 할 수 없다(오남용 방지).
- **서버가 없어도 서비스가 멈추지 않게** 모든 실패를 규칙 대체로 흡수한다.

**검증** — 평가 121문항(직접 34·구어체 53·복합 10·응급 10·무관 7·함정 7): 모델 1 100%, 모델 2 99.2%. 평균 응답 약 0.4~0.6초, 형식 오류 0건. 백엔드 30개·프론트 11개 테스트(서버 실패 시 대체, 질문 문장 로그 미기록 등). 실제 서버를 띄워 브라우저에서 복합 질문 → 이동 → 칩 → 이어서 이동까지 확인.

### 13. 응급 규칙 보강과 LLM 이중 검사

**무엇** — 응급 판별은 가장 틀리면 안 되는 부분인데, 평가에서 응급 문장 10개 중 규칙이 5개만 잡았다("가슴이 **너무** 아파요" 등이 "이해하지 못했어요"로 처리됨). 이를 고쳤다.

**어떻게**
- 기존 정규식은 "가슴이 아파요"처럼 정해진 어순만 허용했다. 사이에 부사·조사가 들어가도 잡도록 패턴을 넓혔다(가슴·심장, 호흡, 의식·쓰러짐, 출혈, 뇌졸중 의심, 마비·경련).
- 의료진 검수 전 임시 항목을 추가했다: 자해·극단적 선택, 중독·과다 복용, 아나필락시스, 임신 중 출혈.
- **오탐 방지**를 테스트로 고정했다("숨은 맛집 차 한잔", "정신이 없어요 바빠서", "다리에 힘이 없어요", "갑자기 어깨가 결려요").
- LLM도 응급을 판단한다(프롬프트에 응급 정의). **규칙 또는 LLM 중 하나라도 응급이면 응급**으로 처리한다.

**사용한 스킬** — 정규식 설계(문맥 제한, 선택적 부사), 실패 테스트 먼저 작성(22건 실패 → 통과), 오탐/미탐 균형 판단(놓치는 위험 > 불필요한 안내), 평가 문항으로 회귀 확인

**설계 이유** — 응급에서는 놓치는 비용이 훨씬 커서 넓게 잡는다. 대신 일상 표현과 겹치는 단어는 문맥으로 걸러 불필요한 119 안내를 줄인다. 규칙은 서버가 없을 때도 동작하므로 LLM 이중 검사와 별개로 유지한다.

**남은 일** — 이 목록은 의료진 검수를 받은 것이 아니다. 극단적 선택 문구의 전용 안내(상담전화 등)도 정해야 한다([작업목록](작업목록.md) E).

### 14. LLM 평가 스크립트

**무엇** — 정답이 붙은 문장 121개를 모델마다 한 건씩 보내 정확도·응답 시간·형식 오류·응급 재현율을 표로 비교한다. 프롬프트나 모델을 바꿀 때 회귀를 확인하는 데도 쓴다.

**어떻게** — `frontend/scripts/llm-eval/run.ts`(vite-node)가 `cases.json`을 읽어 `models.local.json`의 모델에 요청한다. 프롬프트와 출력 스키마는 백엔드가 쓰는 파일을 그대로 읽어 평가와 운영이 같은 조건이다. 현재 규칙 판별기(`routeQuestion`)를 같은 표에 넣어 규칙 대비 개선폭을 본다.

**사용한 스킬** — 평가 문항 설계(직접·구어체·복합·응급·무관·함정), 오류 유형별 집계, 지연 시간 분위수(p50·p95), 사내 주소를 로컬 전용 파일로 분리

**한계** — 문항을 직접 작성해 프롬프트와 겹치는 예시가 있고(점수 낙관), 순차 호출이라 동시 접속 부하는 측정하지 않았다.

**평가 결과 (121문항, 같은 프롬프트, 한 번에 1건씩)**

| 모델 | 전체 | 구어체 | 복합 | 응급 | 평균 응답 | 비고 |
|---|---|---|---|---|---|---|
| 모델 1 (대형) | 100% | 100% | 100% | 100% | 약 0.6초 | 오답 0건 |
| 모델 2 (대형, 생각 모드 끔) | 99.2% | 100% | 100% | 100% | 약 0.4초 | 오답 1건(무관 문장을 예약 조회로) |
| **모델 3 (소형, 사내 서버 배포에 사용)** | **97.5%** | 98.1% | 100% | 90% | 약 0.9초 (p95 1.2초) | 오답 3건 |
| 현재 규칙만 | 57.9% | 35.8% | 0% | 100% | — | 복합 질문은 처리 못 함 |

- 모델 3의 오답 3건: "배가 아프고 숨이 차요"(응급을 증상 안내로), "발렛 서비스도 있어요"(주차 안내를 모름으로), "건강보험료 얼마 내야 해요"(무관을 건강 정보로). 응급 1건은 **응급 규칙이 먼저 잡으므로** 실제 챗봇에서는 119 안내가 나온다 — 규칙을 LLM으로 대체하지 않는 이유다.
- 세 모델 모두 형식 오류는 0건이었다(구조화 출력).
- 모델 3은 동시 처리 수가 제한되어 있어 여러 명이 동시에 쓸 때의 성능은 측정하지 못했다.

### 15. 사내 서버 Docker 배포, 접속 로그인(선택)

**무엇** — 챗봇(화면 + 질문 분류 API)을 사내 서버(리눅스)에 **컨테이너 1개로 추가**했다. 서버에는 다른 서비스가 이미 돌고 있어서 그 서비스를 건드리지 않는 것이 조건이었다. 서버에서 이미지를 직접 빌드해 실행했고(레지스트리 push 없음), 브라우저 접속과 LLM 분류 동작을 확인했다(2026-10-14).

**어떻게**
```
내 PC: git archive 로 소스 묶기 ─ scp ─▶ 서버 /tmp
서버 : 풀기 → .env 작성(서버 주소·모델·계정) → 설정 검증(docker compose config)
       → docker compose up -d --build --no-deps chatbot   (서비스 이름을 지정, 이 서비스만)
       → 상태·health·LLM 동작·기존 컨테이너 영향 확인
```
- **구성(`docker/chatpoc/`)**: 독립 compose 프로젝트(`chatpoc`), 서비스 `chatbot`, 컨테이너 `chatpoc-chatbot`, 전용 네트워크 `chatpoc_net`, 볼륨 없음, 호스트 포트는 `.env`의 `CHATPOC_PORT`(기본 18080).
- **이미지**: 멀티 스테이지(Node로 화면 빌드 → Python 이미지에 서버와 화면을 담음), 일반 사용자로 실행, 읽기 전용 파일시스템, 권한 제거, health check.
- **설정 위치**: 서버 주소·모델·API 키·접속 아이디/비밀번호는 서버의 `docker/chatpoc/.env` 한 곳. 저장소·이미지·로그에 남지 않는다(`.gitignore`, `.dockerignore`).
- **접속 로그인(선택)**: `CHATBOT_BASIC_USER/PASSWORD`를 둘 다 채우면 HTTP Basic 인증을 요구한다. 비우면 사내망에서 누구나 접속한다. `/health`는 컨테이너 상태 확인용으로 열려 있다.
- **작업 원칙**: 기존 서비스는 중지·삭제·재생성하지 않는다, `docker compose down`과 서비스 이름 없는 전체 `up -d`를 쓰지 않는다, 기존 서비스에 영향이 있는 변경은 먼저 확인받는다, 허용 범위는 챗봇에 한정한다. 문서(`docker/chatpoc/README.md`)와 `CLAUDE.md`에 명시했다.

**사용한 스킬** — Docker(멀티 스테이지 빌드, 비루트·읽기 전용 실행, health check), Docker Compose(프로젝트 분리, 서비스 지정 기동, `--no-deps`, env_file), SSH/scp로 서버 작업, `git archive`로 소스 전달, 서버 작업 원칙 설계(영향 범위 제한·확인 절차), HTTP Basic 인증 구현(상수 시간 비교, 선택 기능), 환경변수 기반 설정 분리, 읽기 전용 사전 점검 절차

**설계 이유**
- **독립 프로젝트로 분리**: 같은 서버의 기존 compose 파일을 수정하면 기존 컨테이너가 재생성될 수 있어서, 이름·네트워크·포트·볼륨을 모두 새로 만들어 영향 범위를 챗봇 하나로 한정했다.
- **서비스 이름 지정 기동**: 서비스 이름을 쓰지 않는 `up -d`나 `down`은 실수로 다른 대상까지 건드릴 수 있어 절차에서 제외했다.
- **서버에서 직접 빌드**: 레지스트리가 없어도 되고, 소스 파일만 보내면 된다. 서버가 외부에 못 나가면 이미지를 파일로 옮기는 예외 절차를 문서에 두었다.
- **계정은 `.env`에서 직접**: 아이디·비밀번호를 채팅이나 저장소에 남기지 않고 서버 운영자가 직접 입력한다.

**검증** — 서버에서 이미지 빌드(약 27초) → 네트워크·컨테이너 생성 → `healthy` → 챗봇 화면 접속 → 질문 입력 시 LLM 분류 동작을 확인했다. 컨테이너 네트워크 대역이 사내 LLM 서버 대역과 겹치지 않음을 확인했다. 백엔드 테스트 42개(로그인 8개, API 키 1개 포함)와 compose 구조 점검을 통과했다.

**남은 일** — 기존 컨테이너 가동 시간 비교(영향 없음)의 최종 확인, 접속 로그인 설정 여부 결정, https(사내 인증서) 검토, 서버 코드 갱신 절차 정착, 모델 동시 처리 한계 점검([작업목록](작업목록.md) A·E).

#### 마크업·스타일
- **CSS 변수(디자인 토큰)**: `site/index.html`의 `:root`에 색·헤더 높이를 변수로 두고 전 화면에서 참조 → 색 교체가 한 곳에서 끝난다.
- **scroll-snap**: PC에서만 섹션 단위 스냅. 모바일은 `scroll-snap-type: none`으로 풀어 자연 스크롤을 유지한다.
- **CSS Modules**: 챗봇 컴포넌트별 `.module.css`로 클래스 이름 충돌을 막았다.
- 재사용 팁: 새 프로젝트에서도 색·간격은 변수로 시작하고, 모바일 breakpoint는 한두 개(900px, 400px 등)로 단순하게 둔다.

#### 브라우저 스크립트
- **Pointer Events + `setPointerCapture`**: 마우스·터치를 한 코드로 처리하고, 포인터가 창 밖으로 나가도 드래그가 끊기지 않는다.
- **`fetch` + `AbortSignal.timeout`**: 개발 서버 존재를 800ms 안에 확인해 대체 주소로 넘어간다.
- **Clipboard API**: 실패(권한·비보안 컨텍스트) 시 사용자에게 대안 안내를 보여 준다.
- **localStorage**: 모든 읽기·쓰기를 `try/catch`로 감싸고, 실패해도 화면은 동작하게 한다.

#### React·TypeScript
- **판별 유니온**: `RouteResult = emergency | intent | unknown`처럼 결과 종류를 타입으로 고정해 분기 누락을 컴파일 단계에서 잡는다.
- **상태 구조**: 화면 전환·연결 주소·말풍선(`echo`)·현재 화면(`screen`)을 `App` 한 곳에서 관리하고, 하위 컴포넌트는 props로만 받는다.
- **설정 주도 UI**: 설정 화면의 항목이 `config`에서 만들어지므로 메뉴가 늘어도 코드를 고치지 않는다.

#### 임베드·메시징·보안
- **`postMessage` 프로토콜**: `{ type: 'chatpoc:query', text, topic }`. 보낼 때 `targetOrigin`을 같은 사이트로 제한하고, 받을 때 `e.origin`과 `e.source === window.parent`를 둘 다 확인한다. 외부 사이트로는 보내지 않는다.
- **개인정보**: 증상 문구를 URL 쿼리(`?q=`)에 넣지 않는다. 주소·서버 로그·브라우저 기록에 남을 수 있기 때문이다.
- **URL 검증**: 사용자가 등록하는 주소는 `/`로 시작하는 경로 또는 http(s)만 허용한다(`javascript:` 차단).
- **안전한 렌더링**: 연결 페이지는 `textContent`로만 값을 넣는다.

#### 접근성
- 추천 질문 목록은 `role="combobox"` + `listbox`/`option`, `aria-activedescendant`로 키보드·스크린 리더에서 선택 위치를 알린다.
- 토스트·안내는 `role="status"`/`aria-live="polite"`, 오류는 `role="alert"`.
- 아이콘만 있는 버튼에는 `aria-label`을 붙인다.

#### 질문 판별
- 규칙은 **위에서부터 먼저 맞는 것**을 쓴다 → 구체적인 규칙을 위에 둔다.
- **응급이 항상 먼저**: 추천 질문(`routeSuggestion`)에서도 응급 검사를 건너뛰지 않는다.
- **오탐 방지 테스트**를 같이 쓴다("배송", "배우고"). 규칙을 늘릴 때마다 이런 반례를 먼저 적는다.
- 재사용 팁: 판별 결과 타입을 고정해 두면 키워드 → AI 판별 교체 때 호출부를 건드리지 않는다.

#### 데이터 편집·변환 (엑셀 → JSON)
- 변환 함수는 **순수 함수**(`buildSuggestions`), 파일 읽기·쓰기는 얇은 스크립트(`sync-suggestions.mjs`)로 분리했다.
- 오류는 `'시트' N행: 원인` 형식으로 모아서 한 번에 보여 준다.
- 엑셀이 열려 있어 읽기 실패하면 "저장하고 닫은 뒤 다시 실행" 안내가 나온다.
- 원본(xlsx)과 생성물(json)을 **같은 커밋**에 넣어 어긋남을 막는다.
- 재사용 팁: 메뉴·문구·FAQ처럼 비개발자가 고치는 데이터는 같은 방식(엑셀 → 검증 → JSON)으로 옮길 수 있다.

#### 테스트
- `it.each`로 표현 변형을 표처럼 나열하고, 판별기·추천 질문·변환 로직을 모두 단위 테스트로 고정했다.
- 데이터가 바뀌어도 깨지는 곳을 잡는 **일관성 테스트**를 뒀다(추천 질문의 기능 키가 알려진 기능인지, 응급 문구가 섞이지 않았는지).
- 한계: 화면 흐름(E2E) 테스트는 아직 없다([작업목록](작업목록.md) F).

#### 빌드·도구
- **Vite API 직접 호출**: `build({ root, base, build: { outDir } })`. Windows Git Bash가 `/chat/` 같은 인자를 경로로 바꾸는 문제를 피하고, 환경변수로 base를 바꾼다.
- **`npm ci`**: 잠금 파일 그대로 설치해 CI와 로컬의 결과가 같다.
- **환경변수**: 백엔드 주소 `VITE_API_BASE`, 사이트 경로 `SITE_BASE`.

#### 백엔드
- FastAPI 라우터를 기능별 폴더(`features/config/`)로 나누고, 스키마는 Pydantic 모델로 정의했다.
- 프론트 TS 타입과 이름을 맞추려고 `alias_generator=to_camel`을 썼다.
- 현재 미배포. 배포 시 `CORS_ORIGINS`를 프론트 주소로 지정한다.

#### LLM 연동·평가
- **구조화 출력**: 모델이 자유 문장 대신 JSON 스키마에 맞는 값만 내게 한다(기능·주제는 enum). 파싱 실패와 엉뚱한 값이 크게 줄어, 평가에서 형식 오류가 0건이었다.
- **응답은 한 번 더 검증**한다: 스키마를 믿지 않고 `normalize`가 모르는 값 제거·중복 제거·응급 우선·최대 3개를 서버에서 다시 보장한다.
- **분류에는 생각 모드를 끈다**: 일부 모델 계열은 기본이 추론(생각) 모드라 `enable_thinking=false`로 끄면 빠르고 형식이 안정적이다.
- **모델 대체(failover)**: 1순위 오류·형식 불일치 시 2순위, 모두 실패하면 503 → 프론트가 규칙으로 대체한다. 서비스는 멈추지 않는다.
- **평가 설계**: 정답 문항을 유형(직접·구어체·복합·응급·무관·함정)으로 나누고, 현재 방식(규칙)을 같은 표에 넣어 개선 폭을 본다. 응급은 재현율을, 일반은 정확도·지연·형식 오류를 본다.
- **평가의 한계 인정**: 문항을 직접 썼고 프롬프트와 겹치는 예시가 있어 점수가 낙관적이다. 운영 전에는 실제 질문으로 다시 측정한다.
- 재사용 팁: 프롬프트·스키마를 코드 옆 파일로 두면 평가와 운영이 같은 조건이 된다.

#### 보안·개인정보
- **질문 문장은 서버 로그에 남기지 않는다**(기능과 걸린 시간만). 테스트로 고정했다.
- **공개 저장소에는 사내 서버 주소·모델 이름을 두지 않는다**. 환경변수와 `*.local.*` 파일(.gitignore)만 쓰고, 설정이 없으면 기능을 끄는 쪽으로 동작한다.
- push 전에 커밋 기록까지 검사한다: 한 번 올라간 정보는 지워도 남기 때문에, 올리기 전 기록을 다시 만들었다.
- 중간 서버는 입력 길이를 제한하고 출력을 기능 목록으로 제한해, 일반 대화용으로 오남용하기 어렵게 했다.

#### 배포·자동화
- **GitHub Actions**: `defaults.run.working-directory`는 `run` 단계에만 적용되고 `uses`의 `path`는 저장소 루트 기준이다(아래 "겪은 문제" 참고).
- **Pages 환경**: `environment: github-pages`와 `deploy-pages`가 주소를 출력한다.
- **하위 경로**: 프로젝트 사이트(`<조직>.github.io/<저장소>/`)는 도메인 루트가 아니라서 base 경로를 빌드에 알려 줘야 한다.

#### 협업·프로세스
- **브랜치 → PR → 머지** 흐름. 버그 수정 1개 = 커밋 1개, 리팩토링과 기능 추가를 섞지 않는다.
- **CLAUDE.md로 인수인계**: 구조, 명령어, 작업 순서, 주의 사항을 파일에 적어 두면 사람이든 AI든 같은 맥락에서 이어 간다.
- **문서 분리**: 정리(무엇을 했나)와 목록(무엇을 할 것인가)을 나눠 각각 갱신한다.

## 5. 설계 원칙과 의사결정 기록

| 결정 | 이유 | 대안 / 한계 |
|---|---|---|
| 응급 판별은 규칙으로 가장 먼저 | 의료 도메인에서 예측 가능해야 하고 AI 실패와 무관하게 동작해야 함 | AI 판별은 응급 이후 단계에서만 사용 |
| 키워드 규칙으로 시작 | 백엔드·API 키 없이 POC 동작, 규칙이 눈에 보여 검증 쉬움 | 표현이 다양해지면 한계 → AI 판별 계획 |
| 프론트만 배포 + 목업 | 정적 호스팅(무료)만으로 데모 가능 | 설정 변경은 코드 수정 필요 |
| `intent` 키로 기능 연결 | 메뉴·판별·추천·연결 주소가 키 하나로 이어짐 | 키 오타 위험 → 테스트로 방지 |
| 연결 주소를 localStorage에 저장 | POC에서 서버 없이 설정 체험 | 사용자마다 따로 → 백엔드 저장 필요 |
| 입력 문구는 postMessage | URL·로그에 건강 정보가 남지 않게 | 같은 사이트 페이지에만 전달 가능 |
| 엑셀 → JSON | 비개발자 편집, 파일 하나로 단순 | 한 번에 한 사람만 편집, 동기화 명령 필요 |
| 연결 안 된 질문도 표시 | 엑셀에서 '사용'인 질문이 사라지면 혼란 | 누르면 "준비중" |
| iframe 위젯 | 메인과 챗봇의 스타일·배포 분리 | iframe 표시를 막는 외부 사이트는 "새 창" |
| Pages 자동 배포 + 공개 저장소 | 머지 = 배포, 무료 | 공개되므로 가상 데이터만 유지 |
| 직접 입력은 "응급 규칙 → LLM(전부) → 규칙 대체" | 규칙 먼저 방식은 규칙의 오탐을 물려받아 94.5%, LLM 단독 100% | LLM 호출 때문에 응답이 약 0.5초 늘고 서버가 필요 → 없으면 규칙 모드 |
| 중간 서버를 사내 PC 1대에서 실행 | 사내 LLM은 브라우저에서 직접 못 부름(사내 주소, https→http 차단), 프롬프트 노출 방지 | PC가 꺼지면 중단. 운영은 별도 서버 필요 |
| 응급은 규칙과 LLM 중 하나라도 응급이면 응급 | 놓치는 비용이 불필요한 119 안내보다 큼 | 과잉 안내 감수, 규칙 패턴은 의료진 검수 필요 |
| 사내 서버 주소·모델 이름은 코드에 두지 않음 | 공개 저장소에 사내 정보가 남지 않게 | 실행할 때 환경변수·로컬 파일 설정 필요 |
| 복합 질문은 첫 기능으로 이동 + 나머지는 칩 | 챗봇 안 화면이 하나라 동시에 못 연다. 질문이 사라지지 않음 | 한 번에 하나씩 확인 |
| 사내 서버는 독립 compose 프로젝트로 추가 | 같은 서버의 기존 서비스를 수정·재생성하지 않기 위해 이름·네트워크·포트·볼륨을 모두 분리 | 기존 compose에 합치는 방법은 기존 파일 수정이 필요해 예외(확인 후)로만 허용 |
| `docker compose down`·전체 `up -d`를 쓰지 않고 서비스 이름을 지정 | 실수로 다른 컨테이너까지 건드리는 것을 막음 | 제거는 `rm -sf chatbot`처럼 대상을 지정 |
| 서버에서 소스로 직접 이미지 빌드 | 레지스트리 없이 소스 파일만 전달하면 됨 | 서버가 외부에 못 나가면 이미지를 파일로 옮김 |
| 서버 주소·계정은 서버의 `.env` 한 곳 | 저장소·이미지·로그에 남기지 않고 운영자가 직접 입력 | `.env` 권한 관리 필요(600) |
| 접속 로그인은 선택 기능(기본 꺼짐) | 데모에서는 번거롭지 않게, 필요하면 켬 | 꺼 두면 사내망의 누구나 접속. http라 평문 → 실사용은 https 필요 |
| 사내 서버 모델은 소형으로 시작 | 이미 서버에 배포된 모델이라 추가 구성이 필요 없음. 평가에서 97.5% | 동시 처리 제한 → 사용자가 늘면 모델 1·2로 전환(`.env`만 수정) |
| 응급 규칙은 모델이 바뀌어도 그대로 앞에 둠 | 모델 3이 응급 1건을 놓쳤으나 규칙이 잡음 | 규칙 패턴은 의료진 검수 필요 |

## 6. 겪은 문제와 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| `vite build --base /chat/`가 깨짐 | Windows Git Bash가 `/`로 시작하는 인자를 경로로 변환 | `build:site` 스크립트에서 Vite API 직접 호출 |
| PowerShell에서 `npm` 실행 거부 | 실행 정책으로 `npm.ps1` 차단 | `npm.cmd` 또는 `node node_modules/...`로 직접 실행 |
| `--out` 경로에 공백이 있으면 빌드 실패 | `npm run`이 인자를 공백으로 분리 | 공백 없는 경로 사용 |
| (Netlify 시절) zip 업로드 시 사이트 깨짐 | PowerShell 5.1 `Compress-Archive`가 경로를 `\`로 저장 | .NET `ZipArchive`로 `/` 경로 사용 |
| (Netlify 시절) 머지해도 운영 주소가 안 바뀜 | 수동 드래그 배포, GitHub 연결 없음(조직 비공개는 유료) | GitHub Actions + Pages 자동 배포 |
| Pages에서 챗봇 자원 404 예상 | 챗봇이 `/chat/` 기준으로 빌드되는데 사이트는 `/hospital-chat-poc/` 아래 | `SITE_BASE`로 `/hospital-chat-poc/chat/` 기준 빌드 |
| 연결 페이지 기본 주소가 사이트 밖으로 향함 | `DEFAULT_LINKS`가 절대 경로 `/pages/...` | `import.meta.env.BASE_URL`에서 사이트 루트 계산 |
| 워크플로가 올릴 폴더가 없음 | `build:site`는 `deploy/`에 쓰는데 업로드는 `production-site` | `--out ../production-site`로 일치시킴 |
| `npm run dev`가 깨짐 | `vite.config.ts`에 `base`/`outDir`을 넣고 `/v1` 프록시를 지움 | 설정을 원래대로 되돌리고 값은 스크립트에서 주입 |
| `main`에 직접 올라간 워크플로와 충돌 | 같은 파일을 서로 다르게 수정 | 수정본을 기준으로 병합 커밋 후 PR |
| 무료 플랜 비공개 저장소에서 Pages 불가 | GitHub Pages 요금 정책 | 저장소 공개 전환(비밀 값·실제 정보 점검 후) |
| 엑셀을 열어 둔 채 동기화하면 읽기 실패 | 파일 잠금 | 오류 메시지에 "저장하고 닫은 뒤 다시" 안내 |
| "가슴이 너무 아파요"가 응급으로 안 잡힘 | 응급 정규식이 "가슴이 아파요"처럼 정해진 어순만 허용(응급 10문장 중 5개 미탐) | 부사·조사·어순 변형을 허용하도록 패턴 확대, 실패 테스트 22건을 먼저 만들고 수정. 규칙·LLM 이중 검사 |
| 규칙→LLM 보완 방식의 정확도가 LLM 단독보다 낮음 | 규칙이 틀린 답을 자신 있게 내면(버스 기사님, 예약석 식당) LLM이 개입하지 못함 | 응급 규칙만 먼저 두고 나머지는 LLM이 판단하게 구조 변경 |
| 사내 서버 주소·모델 이름이 공개 저장소 코드에 들어감 | 기본값으로 설정 파일·README·평가 스크립트에 하드코딩 | push 전에 발견 → 환경변수·로컬 파일로 분리하고 커밋 기록까지 다시 만듦. `CLAUDE.md`에 규칙 추가 |
| 서버가 시작되지 않음(Windows) | `ZoneInfo("Asia/Seoul")`에 필요한 시간대 데이터(tzdata)가 Windows에 없음 | `requirements.txt`에 `tzdata` 추가 |
| 평가 점수 해석 | 문항이 프롬프트 예시와 겹치고 직접 작성해 낙관적 | 한계를 문서에 명시하고, 운영 전 실제 질문으로 재평가를 작업목록에 추가 |
| 배포 파일을 `deploy/chatpoc`에 두려 함 | 저장소 루트 `deploy/`는 `build:site`의 기본 출력 폴더라 실행할 때마다 통째로 지워짐 | `docker/chatpoc`로 이동하고 CLAUDE.md에 주의 사항 기록 |
| 서버 컨테이너 네트워크가 사내 LLM 서버 대역을 가져갈 위험 | Docker가 사설 대역을 자동 할당하며 사내 서버 대역과 겹치면 LLM으로 가는 길이 막힘 | 생성 후 대역 확인(`docker network inspect`)을 절차에 포함, 겹치면 대역 고정 설정 추가(이번에는 겹치지 않음) |
| PowerShell에서 `curl` 사용 시 "Uri 값을 제공하십시오" | `curl`이 `Invoke-WebRequest` 별칭이라 `-s`를 다른 옵션으로 해석 | `Invoke-RestMethod` 또는 `curl.exe`를 사용 |
| `scp ...:8000:/tmp/` 형식 오류 | scp는 `IP:` 뒤를 서버 안의 경로로 읽음. 포트는 옵션 `-P` | `scp -P <포트> 파일 계정@IP:/tmp/` 형식으로 설명 |
| 콘솔에서 한글만 입력되고 영문(`yes`)이 입력되지 않음 | 창에 포커스가 없었음(커서가 속이 빈 네모) | 창을 클릭해 포커스를 주고 Git Bash에서 진행 |
| 서버 `/opt`에 폴더 생성 불가(permission denied) | 일반 계정에 쓰기 권한이 없음 | 권한을 바꾸지 않고 홈 폴더(`~/chatpoc`)에 풀어 진행 |
| `.env.example`에 계정 값이 들어간 채 수정됨 | 예시 파일(추적 파일)에 실제 아이디·비밀번호를 입력한 것으로 보임 | 커밋하지 않고 실제 값은 `.env`(추적 제외)에만 두도록 안내. 저장소가 공개라 커밋·push 전 확인이 필수 |

## 7. 다른 프로젝트에 가져다 쓰는 법

**재사용하기 좋은 조각**

| 조각 | 위치 | 쓰임 |
|---|---|---|
| 엑셀 → JSON 파이프라인 | `frontend/scripts/suggestionsFromRows.mjs`, `sync-suggestions.mjs` | 비개발자가 고치는 목록 데이터(메뉴, FAQ, 문구) |
| 질문 판별기 구조 | `frontend/src/shared/chat/intentRouter.ts` | 규칙 우선순위 + 응급 우선 + 타입 고정 결과 |
| 연결 주소 저장소 | `frontend/src/shared/links/linkStore.ts` | 브라우저 저장 → 서버 저장으로 교체하기 쉬운 경계 |
| iframe 위젯 | `site/index.html`의 위젯 스크립트 | 어떤 정적 페이지에든 붙이는 챗봇 창(끌어서 이동 포함) |
| 페이지 ↔ 챗봇 메시지 | `PageViewer.tsx`, `directions.html` | origin 검사가 들어간 postMessage 패턴 |
| Pages 배포 워크플로 | `.github/workflows/deploy.yml`, `build-site.mjs` | `SITE_BASE` 하위 경로 배포 |
| LLM 분류 서버 | `backend/app/features/chat/` (`service.py`, `intent_prompt.txt`, `intent_schema.json`) | 구조화 출력·검증·대체 모델. 프롬프트·스키마를 평가와 공유 |
| 서버 호출 + 규칙 대체 | `frontend/src/shared/chat/llmRouter.ts`, `App.tsx`의 `ask` | 서버가 없어도 멈추지 않는 호출 패턴, 복합 질문 칩 |
| LLM 평가 | `frontend/scripts/llm-eval/` | 문항 세트와 비교 표. 모델·프롬프트 변경 시 회귀 확인 |
| 서버 컨테이너 배포 | `docker/chatpoc/` (`Dockerfile`, `docker-compose.yml`, `.env.example`, `README.md`) | 기존 서비스를 건드리지 않는 독립 compose 구성과 서버 작업 원칙, 단계별 절차 |
| 선택적 접속 로그인 | `backend/app/access.py` | 환경변수가 있을 때만 켜지는 HTTP Basic 인증 미들웨어(상수 시간 비교) |
| 개발 규칙 문서 | `CLAUDE.md` | 구조·명령어·작업 순서·주의 사항 인수인계 틀 |

**새 프로젝트 시작 체크리스트**

1. 저장소·폴더 구조를 정한다(화면 / 공용 / 데이터 / 스크립트 / 배포).
2. `CLAUDE.md`에 구조, 명령어, 작업 순서, 금지 사항을 먼저 쓴다.
3. 기능 키(`intent`)와 설정 데이터의 모양을 정한다 — 이후 모든 기능이 이 키로 연결된다.
4. 판별·검증처럼 **틀리면 안 되는 로직**은 순수 함수로 짜고 테스트부터 쓴다.
5. 비개발자가 고칠 데이터는 엑셀 → 검증 → JSON 흐름을 쓴다.
6. 배포는 처음부터 자동화한다(테스트 통과 시에만 배포). 하위 경로 호스팅이면 base 경로를 환경변수로 받는다.
7. 비공개 저장소라면 Pages·호스팅 요금 조건을 먼저 확인한다.
8. 가상 데이터와 실제 데이터의 경계, 저장소 공개 여부를 정해 둔다.
9. 사내 서버 주소·키·모델 이름은 처음부터 환경변수나 로컬 전용 파일로 받는다(공개 저장소라면 기록에도 남기지 않는다).
10. LLM을 쓰는 기능은 "서버가 없을 때 대체 동작"과 "틀리면 안 되는 부분(응급 등)의 규칙 우선"을 먼저 정하고, 같은 문항 세트로 평가부터 한다.
11. 이미 서비스가 돌고 있는 서버에 올릴 때는 **허용 범위를 먼저 못 박는다**(우리 서비스만). 독립 프로젝트·이름·네트워크·포트로 분리하고, 사전 확인은 읽기만, 기동은 서비스 이름을 지정해서 한다.
12. 서버 작업을 사람이 직접 하는 경우를 위해 "접속 방법 → 파일 전달 → 설정 → 기동 → 확인 → 롤백"을 문서(README)로 만들어 둔다. 계정·주소를 적을 위치(`.env`)를 정해서 알려 준다.
13. 운영 설정 파일의 예시(`.env.example`)에는 값을 비워 두고, 실제 값은 추적되지 않는 파일에만 둔다. 공개 저장소라면 커밋 전에 이 파일의 변경 여부를 확인한다.
